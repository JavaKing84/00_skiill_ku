# 🛠️ Skill 04: 采集与 API 服务解耦的聚合架构

> 拆解对象：[vikiboss/60s](https://github.com/vikiboss/60s)（60s API，100+ 接口的开放数据平台，Deno / CF Workers / Docker 多运行时）
> 一句话结论：**它把"爬虫"和"接口"彻底拆成两个仓库、两个进程、两种故障域** —— 抓取端离线跑定时任务产出静态 JSON，服务端只读 CDN 缓存。这是对抗封锁、做到"毫秒响应"最便宜的架构。
> **所属阶段**：P4 工程化（路线 B） ｜ 前置：P3 打通 ｜ 后续：WS-06

## 🎯 适用场景

- 要抓的东西**更新频率低**（日更、周更、小时更）且**多个数据源**（几十个站点）
- 数据要给多方消费（自己的前端、别人的 App、AI Agent、机器人）
- 抓取端经常被封、经常改版，但**不希望接口跟着挂**
- 想用最低成本扛住高 QPS

不适用：需要实时性到秒级的场景、需要按用户身份动态查询的场景。

## 一、核心架构：三段式解耦

```
┌─────────────────┐      ┌──────────────────┐      ┌─────────────────┐
│ 抓取端（离线）    │ ───> │ 静态数据仓库      │ ───> │ API 服务（在线） │
│ GitHub Actions   │      │ 每天 1 个 JSON   │      │ 边缘函数只读     │
│ 定时 + 重试窗口   │      │ + 图片，走 CDN   │      │ 命中缓存即返回   │
└─────────────────┘      └──────────────────┘      └─────────────────┘
   挂了不影响接口              天然的"数据库"            毫秒级、抗封锁
```

具体落到两个仓库：
- `60s-static-host`：GitHub Actions 定时抓取 → 写 `static/60s/YYYY-MM-DD.json` → commit 回仓库
- `60s`：Deno/Workers 读这些 JSON（或自己现抓），统一包装后返回

**过人之处在于它敢把 GitHub 当数据库用**：
- 免费、天然版本化（每一版数据都能 `git diff` 出来）
- 出错可以 `git revert` 回滚数据（仓库里真有 `REVERT_COMMIT.md`）
- 多 CDN 自动兜底：`cdn.jsdelivr.net` / `cdn.jsdmirror.com` / 自有域名，一条挂了下一条顶上
- 抓取任务失败，接口继续返回昨天/上一个版本的数据，**优雅降级而不是 500**

> 迁移建议：中小型采集项目不需要 Kafka + 时序库。**「定时脚本写文件 + 接口读文件」能解决 80% 的需求**，比上中间件省事一个数量级。

## 二、一接口多形态：`encoding` 参数（最值得抄的设计）

同一个 URL，通过 query 参数切换返回格式：

| `encoding` | 输出 | 目标消费者 |
|---|---|---|
| `json`（默认） | JSON | 程序 |
| `text` | 纯文本，排版友好 | 人类直接看 / 命令行 |
| `markdown` | Markdown | **AI / 支持 md 渲染的客户端（微信、飞书、Notion）** |
| `image` | 302 重定向到图片 CDN 直链 | 省流量、省带宽 |
| `image-proxy` | 代理请求，直接回图片二进制 | 防盗链、跨域 |

```bash
curl "https://60s.viki.moe/v2/60s"                        # JSON
curl "https://60s.viki.moe/v2/60s?encoding=text"          # 纯文本
curl "https://60s.viki.moe/v2/60s?encoding=markdown"      # Markdown
curl "https://60s.viki.moe/v2/60s?encoding=image" -L -o today.png
```

### 为什么这是"过人之处"

1. **一份数据，三种消费形态**。不用为"给机器人推送"再写一个格式化接口。
2. **`markdown` 是 2025 年后的正确默认值**：LLM 和应用内消息卡片都吃 Markdown。你返回 JSON，AI 还得自己拼字符串；返回 Markdown，直接贴就是成品。
3. **`image` 用 302 而不是代理**：把带宽成本转移给 CDN，同时 `image-proxy` 保留给需要防盗链的场景。**默认省钱，必要时可控。**

### 实现骨架（可迁移到 FastAPI）

```python
def render(payload: dict, encoding: str = "json"):
    encoding = (encoding or "json").lower()
    if encoding == "text":     return PlainTextResponse(to_text(payload))
    if encoding == "markdown": return PlainTextResponse(to_md(payload),
                                    media_type="text/markdown; charset=utf-8")
    return JSONResponse({"code": 0, "message": "ok", "data": payload})
```

> 建议：**所有自建数据接口都加上 `encoding=text|markdown`**。写起来 20 行，收益是"AI 能直接消费你的接口"，而这个能力现在是刚需。

## 三、统一契约（三层规范）

### 3.1 响应信封
```json
{ "code": 0, "message": "ok", "data": [ ... ] }
```
`code=0` 表示成功，业务错误码放在 `code` 而不是 HTTP 状态码里。**好处**：前端只需判一个字段；**代价**：HTTP 语义丢了，监控系统看不出错误率。折中做法是 `code != 0` 时同步返回 4xx/5xx，两者都兼得。

### 3.2 时间字段双写（很实用的约定）
```
updated      → "2025/01/13 07:22:32"   （可读）
updated_at   → 1736770800082           （13 位毫秒时间戳）
```
**规则：带 `_at` 后缀 = 时间戳；不带 = 可读字符串。**
好处：前端直接展示不用格式化，程序直接比较不用 `Date.parse`。你只要在文档里写一次这条规则，所有接口自动一致。

### 3.3 语义字段统一命名
```
所有链接/原文 → link
所有封面/主图 → cover
```
**这是"接口设计的最小可预期性"**：消费者不用记"这个接口叫 url，那个叫 href，那个叫 detail_url"。

> 迁移建议：给自己定一条铁律 —— **同一个语义在所有接口里只能有一个字段名**。一旦破例，三个月后你自己都会写错。

## 四、文档本身就是 AI 友好的

`https://docs.60s-api.viki.moe/llms.txt` —— 一份专供 AI 读取的接口索引：

```
## API Docs
- 🕘 周期资讯 [【日更】每天 60 秒读懂世界](...): **如果需要 RSS 订阅，可以使用 /v2/60s/rss 端点**
- 🔥 热门榜单 [【实时】微博热搜](...): 
- 🍱 实用功能 [Whois 查询](...): 优先使用 RDAP 协议数据，然后降级到常规 Whois 本地递归查询。
```

**过人之处**：它把"文档"做成了 **给模型的上下文文件**。任何一个装了 WebFetch 的 Agent，读一个 txt 就知道全部可用接口，不用爬 HTML 文档站。
另外仓库里还有 `CLAUDE.md` / `COPILOT.md` —— **把 AI 协作约定也纳入版本管理**。

> 迁移建议：你的每个内部服务都该有一个 `/llms.txt`，列出：能做什么、接口路径、参数、返回结构、限制。这是成本最低的"让 AI 会用你的系统"。

## 五、多运行时同构（一套代码，五种部署）

```
deno.ts → deno.json        Deno Deploy（主站）
cf-worker.ts → wrangler    Cloudflare Workers
bun.ts → bun                Bun
node.ts (v22.6+, --experimental-strip-types)  Node
Dockerfile → 4399 端口      Docker（自建首选）
```

**关键手法**：**业务代码只写一遍，运行时差异收敛到几个入口文件里**。`src/` 下一个 `app.ts` + `router.ts` + `modules/` + `middlewares/`，入口文件各自把 fetch handler 适配过去。

**为什么值得学**：主域名部署在 Deno Deploy，部分地区被墙 → 用户可以自己 Docker 跑一份。**能自建，才敢依赖。**

配套的还有 **公共实例列表** 页面 —— 官方明确说"主域名每日额度有限、限流严格，仅供调试；生产请自建或使用社区实例"。
这是一种很成熟的产品态度：**不假装自己是免费无限服务，而是把"自建"做成第一公民。**

## 六、抓取端的可靠性设计

### 6.1 重试窗口而非单点定时
```
每半小时自动尝试更新；正常情况最晚上午 10 点会更新
```
**心法**：数据源不是准时给你数据的。与其定 `07:00` 跑一次失败就空一天，不如**在一个窗口内反复尝试，成功即停**。

### 6.2 抓取端用 AI 做结构化
> `60s-static-host` 仓库定时利用 **Gemini 大模型**精准抓取。

这是近两年采集领域最实用的范式转变：**不要把"公众号文章 / 网页正文"用正则切成结构化字段，而是把 HTML/Markdown 整段丢给模型，让它输出 JSON。**
- 正则：改版就崩，维护成本随站点数线性上升
- LLM：改版通常还能扛，提示词里写清楚"找不到就返回 null 不要编"

> 对应本库 [01 号文档](./01_anti_scraping_sop.md) 的第二步：拿到 HTML 只是开始，**结构化的那一步交给模型**往往最划算。

### 6.3 数据校验与图片自渲染
- 生成每日 JSON 后**同时用浏览器渲染一张 PNG 卡片**（`assets/` 里有字体和排版配置），图片和数据同源、同步发布
- 图片生成失败不影响 JSON 发布（两条独立产物）

**启发**：当你做"日报/榜单"类产品，**数据 + 一张图**是完整交付物。用户要的就是能直接转发的图，不是 JSON。

### 6.4 数据源分级与降级链
```
Whois 查询：优先 RDAP 协议 → 降级到常规 Whois 本地递归查询
```
每个接口在文档里**明写数据来源 URL**（如"金价数据来源于 huangjinjiage.cn"、"天气数据来源于腾讯天气"）。
- 出问题时你能立刻定位是哪一层挂了
- 用户能自己判断数据可信度
- 换源时影响面清晰

> 迁移建议：给每个采集函数标注 `source=`，并在返回体里带上 `source` 字段。半年后你会感谢自己。

## 七、接口设计层面的其他细节

| 设计 | 做法 |
|---|---|
| RSS 兼容 | `/v2/60s/rss` 端点，一行代码把 JSON 转 RSS |
| 历史数据 | `/maoyan/realtime/*` 支持 `date=YYYY-MM-DD` 取历史 |
| 多 ID 查询 | 奥运奖牌榜支持指定赛事 ID，默认取最近一场 |
| 缓存 | 智能缓存 + CDN，非实时接口走长缓存 |
| 限流 | 主域名严格限流 + 明确告知额度，引导自建 |
| 生态 | 提供 Agent Skills（`60s-skills` 仓库），可被 AI 直接调用 |

**`date` 参数这条特别值得抄**：只要你的数据是"按天生成"的，就顺手支持 `?date=`。因为你自己的重跑、补数、回溯都需要它，用户的历史查询也需要它 —— 一个参数解决两类需求。

## 八、两种爬虫哲学对照（把 03 和 04 放在一起看）

| 维度 | 03 单站点深度采集 | 04 多源聚合 API |
|---|---|---|
| 目标 | 一个站，挖到底，长期盯 | 几十个站，各挖一层，稳定出数 |
| 时效 | 分钟级（实时监控） | 小时/天级（周期更新） |
| 反爬对抗 | **重度**：指纹、节奏、轮换、熔断 | **轻度**：靠离线抓取 + 分散请求 |
| 失败处理 | 熔断 + 换号 + 通知人工介入 | 静默降级到上一版数据 |
| 存储 | SQLite 事务型，带状态流转 | 静态 JSON，按日期分片，git 版本化 |
| 服务形态 | Web UI + 后台任务 | 无状态只读 API |
| 核心风险 | 账号被封 | 数据源改版 |
| 复用价值 | **系统骨架**（分层、熔断、轮换） | **架构范式**（解耦、多形态、契约） |

**结论**：这两套不是二选一，而是**同一条流水线的两个阶段**。
推荐组合：用 04 的架构做骨架（定时任务产出快照 → 只读接口），把 03 的反爬军火库（熔断、轮换、三层风控探针、拟人节奏）作为"抓取端"的实现细节塞进去。
即：

```
定时调度器 ──> 抓取端（03 的风控/轮换/熔断）──> 快照存储（04 的按日期 JSON / SQLite）
                                                        │
                                              只读 API（04 的 encoding + 统一契约）
```

## ⚠️ 避坑指南

- **别把抓取逻辑塞进 API 请求链路**：用户请求时才去抓 → 一个慢源拖垮整个接口，且必然被封。
- **别只返回 JSON**：至少加 `?format=text|markdown`。AI 消费时代，这是低成本高回报。
- **别让"降级"变成"静默造假"**：返回上一版数据时，要在响应里带 `stale: true` 和 `updated_at`，否则用户拿旧数据做决策。
- **别把时间字段只给一种格式**：可读串 + 时间戳双写，成本几乎为零。
- **别在主域名上做"免费无限"**：明确额度 + 鼓励自建，比限流后被骂好。
- **别用正则去做结构化**：能上模型就上模型，正则留给稳定的小字段。
- **别忘记文档的机器可读版本**：`llms.txt` / OpenAPI JSON / 一段 Markdown 都行，但一定要有。
- **别把 GitHub 当数据库用到超过边界**：单文件别超几十 MB，历史数据要定期归档，否则 clone 会越来越慢。
